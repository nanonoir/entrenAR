# Design: ShipCRM Admin Shipping MVP

## Technical Approach

The `shipcrm` feature introduces the administrative shipping and logistics surfaces into the EntrenAR CRM. The approach relies on existing EntrenAR frontend architecture patterns: route groups for isolation, Zustand for in-memory domain commands (no persistence/localStorage), and React Hook Form + Zod for complex config validation. Shipments will be derived from existing mock sales data. Delivery will be staged in three work-unit commits to respect the 1500-line review budget while submitting a single PR.

## Architecture Decisions

### Decision: Tracking Data Source
**Choice**: Derive read-only `ShipmentTrackingRecord` entities directly from existing mock sales data.
**Alternatives considered**: Create a separate standalone `mock-shipments` array and state sync logic.
**Rationale**: In the MVP, `envioId` equals `ventaId`. Deriving shipments dynamically from the `admin-sales-store` ensures that shipment status always matches sale status without duplicating mock state.

### Decision: Shipping Configuration State
**Choice**: Create a new `admin-shipping-store` (Zustand) with in-memory domain commands for providers and pickup points, explicitly omitting the `persist` middleware.
**Alternatives considered**: Use `localStorage` to persist configurations across reloads.
**Rationale**: Adheres to the PRD requirement (no client-side persistence for admin workflows). The structure prepares for future API integration while avoiding stale client state.

### Decision: Complex Form Validations
**Choice**: React Hook Form + Zod with `@hookform/resolvers/zod`, using `useFieldArray` for schedules and weight ranges.
**Alternatives considered**: Manual `useState` tracking for dynamic arrays.
**Rationale**: RHF+Zod handles dynamic arrays performantly and provides strong types. Zod refinements will validate non-overlapping time ranges and weight tiers, preventing invalid submissions.

### Decision: Filter Drawer Reuse
**Choice**: Implement `ShipmentFilterDrawer` using the exact layout pattern from the existing `ProductFilterDrawer` (scrollable body, fixed footer, draft state).
**Alternatives considered**: Inline filters above the tracking list.
**Rationale**: Consistency with the existing EntrenAR CRM UI/UX, especially for mobile viewports.

## Data Flow

```text
[Mock Sales Data] ────(Derive)────> [Shipment Tracking List/Detail] (Read-only)

[RHF+Zod Forms] ──(Submit)──> [admin-shipping-store]
     │                                │
 (Validate config, schedules)    (In-memory state: Providers, Pickups)
```

## Interfaces / Contracts

```typescript

export interface AdminShippingStore {
  activeTab: "providers" | "pickups";
  providers: ShippingProviderConfig[];
  pickupPoints: PickupPoint[];
  setActiveTab: (tab: "providers" | "pickups") => void;
  saveProviderConfig: (config: ShippingProviderConfig) => void;
  activateProvider: (providerId: ShippingProviderId) => void;
  deactivateProvider: (providerId: ShippingProviderId) => void;
  savePickupPoint: (pickupPoint: PickupPoint) => void;
  activatePickupPoint: (pickupPointId: string) => void;
  deactivatePickupPoint: (pickupPointId: string) => void;
}
```

## Migration / Rollout

No migration required. The feature relies entirely on mock data and in-memory stores. The navigation update will expose the section immediately in the admin sidebar.
